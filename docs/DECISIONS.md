# Decision Log

This file records every key architectural, design and code decision for the profit-aware campaign optimizer. Each entry shows what was chosen and why, which alternatives were considered and why they weren't taken, and what other options remain open.

**Rules**
- Record a decision **when it is made**, not afterwards.
- Never delete an entry. If a decision is reversed, mark the old entry `Superseded by D-0xx` and add a new entry that explains the change.
- A milestone is not complete until its decisions are logged here.
- Log anything a teammate might ask "why did we do it this way?" about. Skip trivial details (naming, formatting).

**Template**

```
## D-0xx: <short title>
- Date: YYYY-MM-DD | Milestone: Mx | Status: Accepted / Superseded by D-0yy
- Context: the problem or question that forced a decision
- Decision: what we chose
- Why: the reasons this option won
- Alternatives considered (and why not taken):
  - <option A>: <reason rejected>
- Other possible alternatives (not evaluated / future options):
  - <option>: <when it might be worth switching>
- Consequences: what this commits us to, risks, follow-ups
- Related: D-0xx, files/modules affected
```

## D-001: Technology stack: Python, scikit-learn, Streamlit
- Date: 2026-11-12 | Milestone: Planning | Status: Accepted
- Context: A hackathon prototype has to work end to end in a short time and be explainable to business stakeholders.
- Decision: Python with pandas, NumPy, scikit-learn, SciPy and Streamlit. No deep learning, no RAG, no multi-agent architecture.
- Why: A mature, well-known stack that is fast to build with. Tabular data with ~45K rows doesn't benefit from deep learning. Streamlit turns Python modules into a dashboard with very little front-end work.
- Alternatives considered (and why not taken):
  - Deep-learning propensity model (e.g. MLP/TabNet): no accuracy gain expected on small tabular data; harder to explain and calibrate.
  - LLM/RAG layer (e.g. a natural-language assistant for RMs): out of scope by the project owner's direction; adds risk without answering the five business questions.
  - Dash or a React front end: more flexible, but much slower to build than Streamlit.
- Other possible alternatives (not evaluated / future options):
  - Gradient-boosting libraries (LightGBM/XGBoost) if accuracy becomes a priority.
  - A FastAPI service plus a separate front end for a production version.
- Consequences: The dashboard is single-user and session-based. Heavy computation (the GA) must be cached and run on demand.
- Related: D-016, D-018

## D-002: uv for project management
- Date: 2026-11-12 | Milestone: Planning | Status: Accepted
- Context: Several team members must reproduce the same environment. The machine has several Python versions (3.11-3.14), and very new versions may lack wheels.
- Decision: Use uv: `pyproject.toml` + `uv.lock`, Python pinned to 3.12 through `.python-version`, `pacopt` as an editable src-layout package, and dependency groups for `dev` and `docs`.
- Why: A single tool manages the Python version, the virtual environment, dependency resolution and the lockfile. It is very fast. `uv sync` gives every teammate an identical environment. Python 3.12 has mature wheels for the whole scientific stack.
- Alternatives considered (and why not taken):
  - pip + venv + requirements.txt: no proper lockfile and no Python version management; environments drift.
  - Poetry: a capable option, but slower, and it doesn't manage Python installs; the project owner chose uv.
  - conda: heavy, and slower to resolve; not needed for pure-Python wheels.
- Other possible alternatives (not evaluated / future options):
  - pixi: if non-Python (conda-only) dependencies are ever needed.
  - Docker image on top of uv: for deployment or a demo on another machine.
- Consequences: Everyone runs commands through `uv run`. `uv.lock` must be committed and kept up to date. The earlier pip-created `.venv` was replaced.
- Related: `pyproject.toml`, `uv.lock`, `.python-version`

## D-003: UCI Bank Marketing `bank-full.csv` as data source
- Date: 2026-11-12 | Milestone: Planning | Status: Accepted
- Context: The project needs realistic customer and campaign data with outcomes, without spending the hackathon on generating synthetic data.
- Decision: Use the UCI Bank Marketing dataset (`bank-full.csv`, 45,211 rows, 17 columns, CC BY 4.0).
- Why: It is public, well documented and contains real campaign outcomes, customer demographics, balances and contact history: everything a propensity model and campaign optimizer need.
- Alternatives considered (and why not taken):
  - Fully synthetic data: takes time and is less credible; results would reflect our own assumptions.
  - `bank-additional-full.csv` (41,188 rows with macro-economic indicators): has no `balance` column, which is our monetary proxy, and the macro indicators are campaign-date features that complicate the pre-campaign framing.
  - Other public datasets (e.g. Santander, Kaggle credit-card churn): they don't contain campaign outcomes for a deposit product.
- Other possible alternatives (not evaluated / future options):
  - The bank's own CRM and transaction data in a real pilot, which would allow true RFM and CLV.
- Consequences: The features are RFM-*inspired* only (no transactions). Balances are in euros from a 2008-2010 Portuguese bank and are shown as £ for illustration.
- Related: D-005, D-014

## D-004: Leakage policy: exclude `duration`, `campaign`, `day`, `month`
- Date: 2026-11-12 | Milestone: Planning | Status: Accepted
- Context: The model must reflect the "morning before the campaign" decision. Some columns are only known after the campaign has started.
- Decision: Exclude `duration` (call length), `campaign` (contacts in the current campaign, partly caused by the outcome), and `day`/`month` (date of the last contact, which reflects the historical calling schedule). Enforce this with an explicit feature allow-list and a guard test. Report an ablation.
- Why: Using these columns would inflate the metrics and produce a model that can't be used before a real campaign. Being honest about leakage is a credibility point in the presentation.
- Alternatives considered (and why not taken):
  - Drop only `duration` (the original spec): `campaign` still leaks (customers who say yes stop being called), and `month` encodes the bank's past calling waves, not customer traits.
  - Keep `campaign` and document the risk: a partly leaky model would still feed money decisions.
- Other possible alternatives (not evaluated / future options):
  - Use *planned* contact intensity as a decision variable in a future uplift model.
  - Use calendar seasonality only as a campaign-timing decision, not a customer feature.
- Consequences: The honest AUC is expected around 0.75-0.78, below figures often quoted for this dataset. The ablation table (M6) shows the gap.
- Related: D-005, D-006, `features.py`, `tests/`

## D-005: RFM-inspired feature definitions
- Date: 2026-11-12 | Milestone: Planning | Status: Accepted
- Context: The project builds on RFM experience, but the dataset has no transaction history.
- Decision: Recency = `pdays` with a never-contacted flag and buckets. Frequency = `previous` (prior-campaign contacts) + a prior-success flag. Monetary proxy = `balance` (also signed-log and quintile). Balance is described as a value indicator, never as revenue.
- Why: Uses only pre-campaign information (D-004) and keeps the RFM vocabulary without overclaiming.
- Alternatives considered (and why not taken):
  - Frequency = `previous + campaign` (original idea): includes the leaky `campaign` column.
  - Treat balance as revenue or CLV: incorrect. Balance is a stock of money, not a flow of profit.
- Other possible alternatives (not evaluated / future options):
  - True RFM from transaction-level data in a real deployment.
  - Product holdings (housing loan, personal loan) as a relationship-depth score.
- Consequences: Feature names and documentation must say "RFM-inspired".
- Related: D-004, D-013

## D-006: Logistic Regression primary, Random Forest challenger
- Date: 2026-11-12 | Milestone: Planning | Status: Accepted
- Context: P_i is multiplied by money in EP_i = P_i x V_i - C_i, so the probability's *calibration* matters as much as ranking. The audience includes business and risk stakeholders.
- Decision: Logistic Regression (one-hot + scaling, `C` tuned on PR-AUC, no class weighting) drives the engines. An isotonic-calibrated Random Forest is trained as a benchmark. The model is switchable in config.
- Why: LR gives well-calibrated probabilities and transparent coefficients and odds ratios, and it is fast enough for interactive re-runs. The RF shows the size of the accuracy-vs-explainability trade-off.
- Alternatives considered (and why not taken):
  - Random Forest only: poorly calibrated raw probabilities and less transparent.
  - Logistic Regression only: gives up the benchmark that shows whether non-linearity matters.
  - Gradient boosting (HistGradientBoosting/XGBoost): often the most accurate, but another tuning and calibration burden for a prototype.
  - `class_weight="balanced"`: distorts the probabilities, which breaks EP.
- Other possible alternatives (not evaluated / future options):
  - Switch to RF or boosting if PR-AUC improves by more than ~0.02 and calibration holds.
  - Generalised additive models (e.g. EBM) for non-linearity that stays explainable.
- Consequences: Non-linear effects must be engineered (age bands, recency buckets). Calibration is checked in M2.
- Related: D-004, D-008, `model.py`

## D-007: Responsible-customer eligibility rules
- Date: 2026-11-12 | Milestone: Planning | Status: Accepted
- Context: The problem statement asks for "responsible customer outcomes". Locking money into a term deposit can harm financially stressed customers. The UK Consumer Duty expects firms to avoid foreseeable harm.
- Decision: Hard-exclude `default = yes`, `balance < 0` and `previous > 10` (contact fatigue). Flag customers aged 75+ and cap them at 2% of the selected list, for human review. Add a reporting-only fairness monitor (targeting rate by age band and job). All thresholds are configurable.
- Why: Removes clear harm cases at low cost (~10% of customers). Avoids discriminating by a protected characteristic (age) while still applying extra care.
- Alternatives considered (and why not taken):
  - Hard-exclude customers aged 75+: blanket exclusion by age is itself an unfair outcome.
  - No eligibility rules: fails the responsible-outcomes requirement.
  - Fairness as a hard optimization constraint: adds complexity, and without demographic parity targets set by the business, any number would be arbitrary.
- Other possible alternatives (not evaluated / future options):
  - Affordability scoring from income and expenditure data.
  - Vulnerability flags from CRM data (bereavement, illness) in a real deployment.
- Consequences: The eligible pool shrinks by ~10%. The 75+ cap becomes a segment constraint in the GA.
- Related: D-010, D-011, `features.py`, `evaluation.py`

## D-008: Term deposit valued as a funding product
- Date: 2026-11-12 | Milestone: Planning | Status: Accepted
- Context: A term deposit is a liability (a funding source), not a lending revenue product. The dataset has no deposit amounts or rates.
- Decision: V_i = D_i x (FTP rate - customer rate) x term - incentive - onboarding, with D_i = clip(D_min + alpha x max(balance, 0), D_min, D_max). EP_i = (P_i - P0_i) x V_i - C_i, and break-even cost BE_i = (P_i - P0_i) x V_i. The deposit principal is never counted as revenue. All parameters are in config and the dashboard sliders.
- Why: This matches how banks value deposits (through funds transfer pricing). It is transparent, and teams can plug in their own assumptions.
- Alternatives considered (and why not taken):
  - Counting the deposit principal as revenue: economically wrong.
  - A flat value per conversion: ignores the differences in deposit size that drive targeting.
  - A NIM-based multi-year CLV model: needs retention and roll-over data we don't have.
- Other possible alternatives (not evaluated / future options):
  - A cannibalisation adjustment: the share of the deposit moved from existing cheaper funding.
  - Roll-over probability and a multi-term lifetime value.
  - Liquidity-regulation value (e.g. LCR/NSFR benefit of stable funding).
- Consequences: The default numbers are illustrative and are calibrated in M3 so that a meaningful share of customers has positive EP.
- Related: D-009, D-015, `economics.py`, `config.py`

## D-009: £50K budget with fully-loaded channel costs
- Date: 2026-11-12 | Milestone: Planning | Status: Accepted
- Context: The brief's example of a £50K budget at £5 per contact pays for 10,000 contacts, i.e. the whole customer universe. The budget would then never force a choice.
- Decision: Keep £50K as the headline budget, but use fully-loaded channel costs: outbound mobile call £12, landline call £10, digital £2. Screen 4 still shows the budget-only upper bound (budget ÷ cost) next to the actual allocation.
- Why: Keeps the brief's headline figure and makes the "limited budget" story real. Fully-loaded costs (agent time, telephony, QA) are more realistic than a bare £5.
- Alternatives considered (and why not taken):
  - £50K at £5 with capacity caps binding: the budget doesn't bind, so the "limited budget" narrative is weak.
  - £20K at £5: changes the brief's headline figure.
- Other possible alternatives (not evaluated / future options):
  - Cost per channel derived from actual bank call-centre data.
  - Variable cost per contact attempt (multiple attempts per customer).
- Consequences: The defaults must be checked in M3 so that the budget actually binds.
- Related: D-008, D-010

## D-010: Binary chromosome with the channel fixed from `contact`
- Date: 2026-11-12 | Milestone: Planning | Status: Accepted
- Context: The brief asks for a binary customer-selection chromosome and also for channel capacity constraints.
- Decision: One gene per eligible customer (select or not). Each customer's channel comes from the dataset's `contact` field (cellular → mobile call, telephone → landline call, unknown → digital). Each channel has its own cost and capacity cap.
- Why: Keeps the chromosome binary as specified, while still enforcing channel constraints. Avoids inventing channel response multipliers the data can't support.
- Alternatives considered (and why not taken):
  - Integer chromosome where the GA picks the channel (skip / digital / call centre / RM): richer, but the response multipliers per channel would be pure assumptions.
  - A single channel with just a contact cap: loses the channel-capacity constraint required by the brief.
- Other possible alternatives (not evaluated / future options):
  - Channel choice as a decision variable once A/B channel-response data exists.
- Consequences: Channel effects on response are learned only through the `contact` feature.
- Related: D-009, D-011, `optimize.py`

## D-011: Constraint handling: repair operator + soft penalty
- Date: 2026-11-12 | Milestone: Planning | Status: Accepted
- Context: GA crossover and mutation create chromosomes that break the budget, contact, channel and segment constraints.
- Decision: A repair operator removes the selected customers with the lowest EP/C until the budget, contact and channel limits hold, then rebalances the segments. A soft penalty is the fallback for segment minimums that repair can't meet.
- Why: Every evaluated solution is feasible, so the reported results are always valid, and the search stays efficient.
- Alternatives considered (and why not taken):
  - Death penalty (discard infeasible children): wastes most of the offspring under tight constraints.
  - Pure penalty function: needs careful penalty tuning, and the best solution can still be infeasible.
  - Constraint-preserving operators only: complex to design for several interacting constraints.
- Other possible alternatives (not evaluated / future options):
  - Multi-objective GA (NSGA-II) trading off profit against fairness or reach.
- Consequences: Repair is greedy-flavoured, which biases the search toward greedy-like solutions. This is why results are reported with and without greedy seeding.
- Related: D-010, D-012, `optimize.py`

## D-012: Strategy comparison set
- Date: 2026-11-12 | Milestone: Planning | Status: Accepted
- Context: Question 5 asks for incremental profit vs the existing strategy. The data has no control group, and the reference chart shows four strategies.
- Decision: Compare Random (proxy for the historical untargeted campaign, averaged over 50 seeds), Propensity-only, Greedy (EP/C), the Genetic Algorithm, Rule-based (highest balance) and the exact MILP optimum (`scipy.optimize.milp`). All strategies go through the same `check_constraints()`.
- Why: Shows the step-by-step value of targeting (Random → Propensity), of profit-awareness (→ Greedy) and of optimizing under interacting constraints (→ GA), with the MILP optimum keeping the GA claim honest.
- Alternatives considered (and why not taken):
  - Random only: hides where the value comes from.
  - Blanket "contact all eligible": not comparable at the same budget.
- Other possible alternatives (not evaluated / future options):
  - Other metaheuristics (simulated annealing, tabu search) as additional benchmarks.
- Consequences: Under a budget-only constraint, greedy is near-optimal, so the default scenario must include interacting constraints for the GA to add value.
- Related: D-011, D-017, `optimize.py`, `evaluation.py`

## D-013: Four-segment propensity-by-value taxonomy
- Date: 2026-11-12 | Milestone: Planning | Status: Accepted
- Context: The Screen 1 reference image shows four segments: High value, Growing, Dormant, Low engagement.
- Decision: Assign segments from a transparent grid: high propensity = top 40% of P_i, high value = V_i at or above the median. High value (high P, high V), Growing (high P, lower V), Dormant (low P, high V), Low engagement (low P, low V). RFM scores and the engagement score are shown as overlays.
- Why: Matches the reference, is easy to explain, and links directly to the decision (P and V are the EP inputs).
- Alternatives considered (and why not taken):
  - k-means clustering: harder to explain; segment labels can change between runs.
  - The classic 11-segment RFM taxonomy (Champions, At Risk, …): built for transaction data we don't have; too granular for the dashboard.
- Other possible alternatives (not evaluated / future options):
  - Thresholds set by the business instead of quantiles.
- Consequences: The segment shares partly follow from the quantile thresholds (by construction).
- Related: D-005, D-017, `segmentation.py`

## D-014: Campaign universe of 10,000 from the held-out test set
- Date: 2026-11-12 | Milestone: Planning | Status: Accepted
- Context: The brief describes a bank with 10,000 customers. Scoring customers the model was trained on would overstate performance.
- Decision: A stratified 70/30 split (`random_state=42`). The 10,000-customer campaign universe is sampled from the 30% held-out test set, so every score is out-of-sample.
- Why: Matches the brief and keeps the backtest (M6) honest.
- Alternatives considered (and why not taken):
  - Score all 45,211 customers: includes training rows, so in-sample scores would be optimistic.
  - Cross-validated out-of-fold scores for every customer: valid but more complex; not needed for a 10,000 universe.
- Other possible alternatives (not evaluated / future options):
  - A time-based split if campaign dates were available as a proper time series.
- Consequences: The test set (~13,564 rows) must be larger than 10,000, which it is.
- Related: D-003, `features.py`

## D-015: Meaning of "incremental" and organic rate P0
- Date: 2026-11-12 | Milestone: Planning | Status: Accepted
- Context: True incremental (causal) uplift needs a control group that wasn't contacted. The dataset contains only contacted customers.
- Decision: "Incremental" means relative to the baseline strategies (D-012). The organic subscription rate P0 defaults to 0 and is configurable. This is stated openly as a limitation.
- Why: Honest about what the data can support, without blocking the prototype.
- Alternatives considered (and why not taken):
  - Uplift / two-model approach: needs treatment and control data we don't have.
- Other possible alternatives (not evaluated / future options):
  - Run a randomised hold-out group in a real campaign, then build an uplift model.
- Consequences: P_i means P(subscribe | contacted). Results must not be described as causal uplift.
- Related: D-008, D-012

## D-020: Commit raw data with a checksum; regenerate processed outputs
- Date: 2026-11-12 | Milestone: M1 | Status: Accepted
- Context: The plan requires the dataset to be in the repository. Processed files and model artifacts are derived from it and change whenever the code changes.
- Decision: Commit `data/raw/bank-full.csv` (4.6 MB) with `bank-names.txt` and a README giving the source, licence, citation and SHA-256. `data.download_raw()` can re-fetch the file and verifies the checksum. `data/processed/` and `artifacts/` are git-ignored and regenerated by the pipeline.

  - Git LFS: unnecessary for a 4.6 MB file, and an extra tool for teammates.
- Other possible alternatives (not evaluated / future options):
  - DVC or a data registry if the data grows or several versions are needed.
- Consequences: Everyone must run the pipeline (or notebook 01) once to create `data/processed/`.
- Related: D-003, `data.py`, `data/raw/README.md`, `.gitignore`

## D-021: Parquet for processed data
- Date: 2026-11-12 | Milestone: M1 | Status: Accepted
- Context: Processed tables carry pandas dtypes (categoricals, int8 flags, NaN recency) that later stages and the app rely on.
- Decision: Store processed tables as Parquet through `pyarrow`, which is added as a runtime dependency.
- Why: Keeps dtypes and categoricals, compresses well, loads fast in Streamlit, and is language-neutral.
- Alternatives considered (and why not taken):
  - CSV: loses dtypes and categories; slower; ambiguous NaN handling.
  - Pickle: tied to the Python/pandas version and unsafe to load from untrusted sources.
  - Feather: similar speed, but less common for long-term storage.
- Other possible alternatives (not evaluated / future options):
  - DuckDB for SQL-style exploration of the processed data.
- Consequences: `pyarrow` (~40 MB) is a dependency.
- Related: `features.save_processed`

## D-022: Feature engineering details (encoding, transforms, bins)
- Date: 2026-11-12 | Milestone: M1 | Status: Accepted
- Context: D-005 fixed the RFM concepts. Implementation needed concrete transforms that suit Logistic Regression (D-006).
- Decision:
  - Keep `"unknown"` as its own category (it carries signal: `contact = unknown` marks customers with no recorded phone channel; `poutcome = unknown` largely means never contacted).
  - Normalise `admin.` to `admin`; map binaries to 0/1.
  - Balance: a signed log transform `sign(b)·log(1+|b|)` for the model, plus quintiles for RFM scoring. The raw balance is kept for economics.
  - Recency: `never_contacted` flag + `recency_days` (NaN = never) + buckets `never / <=90d / 91-180d / 181-365d / >365d`.
  - Frequency: `previous` capped at 10 (the fatigue threshold), plus a `prior_success` flag.
  - Age bands `18-29 / 30-44 / 45-59 / 60-74 / 75+`, alongside numeric age, to capture the U-shaped effect for the linear model.
  - `default` stays a model feature, even though defaulted customers are excluded from targeting. The model is trained on everyone; eligibility is applied at decision time.
- Why: The EDA supports it. The recency buckets are clearly non-monotonic (<=90d: 35%, 181-365d: 18%, >365d: 29%) and conversion rises across balance quintiles (6.9% → 16.4%). A linear model needs these bins and transforms to capture such patterns.
- Alternatives considered (and why not taken):
  - Imputing or dropping `"unknown"`: throws away signal and adds an arbitrary guess.
  - Raw or winsorised balance: the extreme skew (max ~102K) dominates the LR coefficients; signed-log keeps negative values in order.
  - Splines for age and balance: more flexible but harder to explain; bands are enough for a prototype.
- Other possible alternatives (not evaluated / future options):
  - Weight-of-evidence binning (a credit-scoring standard) for even more interpretable LR coefficients.
  - Interaction terms (e.g. prior success × recency) if M2 shows the RF finds strong interactions.
- Consequences: `poutcome` and `prior_success` overlap; the LR regularisation handles this. Recency NaN only exists in `recency_days`, which is not a model feature (the buckets are).
- Related: D-005, D-006, `features.add_rfm_features`

## D-026: Propensity model configuration, evaluation protocol and switch rule
- Date: 2026-11-12 | Milestone: M2 | Status: Accepted
- Context: D-006 chose LR as the primary model with an RF challenger. The concrete settings, how the two are compared, and when the RF would replace the LR all still had to be fixed.
- Decision:
  - **LR:** `StandardScaler` + `OneHotEncoder(handle_unknown="ignore")`. `C` is tuned over (0.003 … 10) with 5-fold stratified CV on average precision (PR-AUC). No `class_weight`. Best C = 0.3 (CV PR-AUC 0.374).
  - **RF:** 300 trees, `min_samples_leaf=50`, `max_features="sqrt"`, wrapped in isotonic `CalibratedClassifierCV`. Not tuned: it is a benchmark.
  - **Evaluation:** ROC-AUC, PR-AUC, Brier, log loss and decile calibration on the full 13,564-row test set. Precision@K for K = 500 / 1,000 / 2,000 and the budget-implied K (contacts the £50K budget buys in propensity order: 4,261 for LR) on the 10,000-customer universe.
  - **Switch rule:** the RF is recommended only if it beats LR PR-AUC by more than 0.02 **and** is at least as well calibrated. The final choice lives in `config.MODEL.selected`.
- Why: PR-AUC suits an 11.7% positive class and the top-of-list decisions the engines make. Class weights would inflate P_i, which is multiplied by money. Measuring precision@K on the universe matches how the list is actually used. A pre-agreed threshold stops the challenger winning on noise. Result: RF +0.016 PR-AUC and a worse calibration gap (1.98 vs 1.22 pp), so LR is kept.
- Alternatives considered (and why not taken):
  - Tuning on ROC-AUC: dominated by the bulk of non-subscribers, which we never contact.
  - `class_weight="balanced"`: distorts the probabilities (D-006).
  - Choosing whichever model scores higher: a 0.016 gain is within seed-to-seed variation and gives up explainability.
  - Precision@K on the whole test set: doesn't reflect the 10,000-customer campaign.
- Other possible alternatives (not evaluated / future options):
  - HistGradientBoosting challenger, or tuning the RF, if a later milestone needs more lift.
  - Bootstrap confidence intervals on the PR-AUC difference, instead of a fixed threshold.
- Consequences: The engines consume `propensity` from `universe_scored.parquet`. The precision key for the budget is the stable `"K=budget"`, and the K itself is stored in `Evaluation.budget_k`, because each model's budget-implied K differs slightly.
- Related: D-006, D-027, `model.py`, `config.ModelConfig`

## D-027: Isotonic calibration of the Logistic Regression
- Date: 2026-11-12 | Milestone: M2 | Status: Accepted
- Context: The tuned LR failed the ≤1.5 pp calibration criterion. Its top decile predicted 39.8% against an observed 43.8% (gap 3.96 pp). That decile is dominated by prior-success customers, where recency and outcome interact in a way a linear model can't fully express.
- Decision: Wrap a clone of the tuned LR pipeline in `CalibratedClassifierCV(method="isotonic", cv=5-fold)`, fitted on the training set. This is the scoring model. The uncalibrated tuned pipeline is kept (`lr_explain`) for coefficients and odds ratios.
- Why: The max gap fell from 3.96 to 1.22 pp, while ROC-AUC (0.753) and the ranking were unchanged. Isotonic regression is monotone, so the coefficient directions and rankings still describe the scoring model.
- Alternatives considered (and why not taken):
  - Platt (sigmoid) scaling: tested, and it didn't fix the top decile. The error isn't sigmoid-shaped.
  - Adding interactions (prior_success × recency) and age splines: tested, with no meaningful calibration gain and a harder-to-explain model.
  - Leaving it uncalibrated: fails the acceptance criterion. A 4 pp under-statement on the best customers biases EP_i downwards exactly where it matters most.
  - Switching to the RF: worse calibration (1.98 pp) and less explainable.
- Other possible alternatives (not evaluated / future options):
  - A separate calibration hold-out (prefit), if the training data grows.
  - Venn-Abers or beta calibration, if isotonic proves unstable.
- Consequences: Isotonic is a step function, so the extreme tail needs a guard (D-028). The saved model holds both the calibrated and the explainable LR (~30 MB joblib).
- Related: D-006, D-026, D-028, `model.fit_lr`

## D-028: Cap the scoring propensity at 90%
- Date: 2026-11-12 | Milestone: M2 | Status: Accepted
- Context: The isotonic tail is fitted on very few customers. On the test set, 8 customers scored a mean of 97.3% but converted at 62.5%. Treating near-certain conversion as real would overstate EP_i and attract the optimiser.
- Decision: `propensity = clip(p_selected, upper=MODEL.propensity_cap)` with a cap of 0.90, applied after calibration. The raw calibrated scores are kept in `p_lr` / `p_rf`. Rank uses the uncapped score, so ties at the cap keep their order. In the universe, 7 customers are capped.
- Why: A simple, transparent, conservative guard. It only lowers scores, never raises them, and affects <0.1% of customers. Decile calibration is unaffected.
- Alternatives considered (and why not taken):
  - No cap: overstated EP for a handful of customers the optimiser would always pick.
  - Platt for the tail only / a blended calibrator: more complex for a tiny group.
  - A lower cap (e.g. 0.70): would distort genuinely strong prospects (the 0.7-0.9 band is well calibrated).
- Other possible alternatives (not evaluated / future options):
  - Shrinking tail scores towards the band mean, or making the cap a Streamlit setting.
- Consequences: The Profit and Optimization engines must use `propensity`, not `p_lr`. Tested: propensity ≤ cap and ≤ p_lr.
- Related: D-027, `model.train_and_evaluate`, `tests/test_model.py`

## D-029: Threading joblib backend for parallel fitting
- Date: 2026-11-12 | Milestone: M2 | Status: Accepted
- Context: GridSearchCV, the RF and permutation importance run in parallel. Under pytest and `nbconvert`, the default `loky` process backend failed intermittently on Windows with `BrokenProcessPool` / `OSError: [WinError 6] The handle is invalid` (worker processes started without a console).
- Decision: Run all fitting and permutation importance inside `joblib.parallel_config(backend=MODEL.parallel_backend)`, with `"threading"` as the default and `n_jobs` from config.

- Other possible alternatives (not evaluated / future options):
  - Switching back to `loky` on Linux CI or servers through config, if it is faster there.
- Consequences: RF results differ at the ~1e-7 level between runs (parallel summation order). The reproducibility test uses `abs=1e-5` for the RF.

## D-032: Segment grid thresholds: top 40% propensity, median value
- Date: 2026-11-12 | Milestone: M3 | Status: Accepted
- Context: D-013 fixed the four segments (High value, Growing, Dormant, Low engagement) as a propensity-by-value grid. The cut-offs still had to be defined.
- Decision: Propensity is "high" at or above the 0.60 quantile of P_i (the top 40%). Value is "high" at or above the median of V_i. Both are quantiles computed on the 10,000-customer universe and stored in `SegmentConfig`. `assign_segments` accepts an explicit `cut` override for what-ifs. Default cut-offs: P ≥ 0.084 and V ≥ £137.67. Counts: High value 2,527, Growing 1,482, Dormant 2,475, Low engagement 3,516.

  - A 50/50 propensity split: the "high" group becomes diluted with customers near the base rate.
- Other possible alternatives (not evaluated / future options):
  - Thresholds set by business owners from campaign targets.
  - Recomputing the quantiles over eligible customers only.
- Consequences: Segment sizes move a little whenever the propensity model or the economics change. Because the value cut is a quantile, scaling the economics leaves memberships unchanged. The M4 segment-share constraints use these labels.

## D-033: RFM and engagement overlays on fixed bins
- Date: 2026-11-12 | Milestone: M3 | Status: Accepted
- Context: The plan asks for RFM scores (1-5) and an engagement score as overlays, not as segments. Classic RFM uses quintiles, but 81% of customers have `previous = 0` and most were never contacted before, so quintiles of R and F can't be formed.
- Decision: R comes from a fixed recency-bucket map (never = 1, >365d = 2, 181-365d = 3, 91-180d = 4, ≤90d = 5). F comes from fixed bins of `previous` (0, 1, 2, 3-4, 5+ → 1-5).   - Equal weights (1/3 each): this would under-weight recency.
  - Using the engagement score as a model feature: it would duplicate features the model already has and add nothing.
- Other possible alternatives (not evaluated / future options):
  - Weights fitted to conversion (a logistic regression on R, F and prior success).
  - Using `campaign` in F, if a post-campaign view is ever needed (excluded now for leakage, D-004).
- Consequences: Most customers score R = 1 and F = 1, which is honest for this data. The scores are display overlays only and play no part in EP or in the optimiser.

## D-035: One shared constraint engine for every strategy, plus an independent checker
- Date: 2026-11-12 | Milestone: M4 | Status: Accepted
- Context: Six strategies (Random, Propensity, Greedy, Rule-based, GA, MILP) must all respect the same budget, contact, channel, segment-share and protected-share limits (plan 4.3). If each strategy enforced the limits its own way, a comparison could reward a strategy for handling a constraint more loosely.
- Decision: Every heuristic strategy is a *priority order* fed through one vectorised constraint engine (`optimize._Engine`). The engine takes customers in order and skips any who would break a limit. It then trims over-represented segments, adds the best members of under-represented ones, and tops up spare capacity. Random = a random order, Propensity = P order, Rule-based = balance order, Greedy = EP/C order. The GA uses the same engine as its repair operator. A separate `check_constraints()` audits every list using only the campaign table and the customer IDs, and returns one row per constraint. Share limits apply to the selected list and are count-based. An empty list is treated as feasible.
- Why: Every strategy is held to identical rules, so differences come from targeting alone. The independent checker catches engine bugs instead of trusting them, and the tests assert both (the engine's violation is 0 and the checker passes). Repair works on the whole (population × customers) matrix at once, which keeps the GA fast.
- Alternatives considered (and why not taken):
  - Each strategy with its own loop: duplicated logic, and inconsistent edge cases (e.g. "stop at first misfit" vs "skip and continue").
  - Penalty-only constraint handling everywhere: heuristics would return infeasible lists that need reporting caveats.
  - Using the MILP's constraint matrix as the checker: not independent of the optimiser code.
- Other possible alternatives (not evaluated / future options):
  - Value-weighted (spend-based) segment shares, if the business sets mix targets in £ rather than head-count.
- Consequences: Segment minimums may add a negative-EP member when the list cannot meet the minimum otherwise. If a segment runs out of members, the rest of the list is shrunk until its minimum share holds. Protected (75+) customers are never added just to meet a minimum. Stress tests over 40 random scenarios plus 3 real stressed scenarios gave 0 infeasible lists.
- Related: D-011, D-012, `optimize.py`, `tests/test_optimize.py`

## D-036: GA operators: gene pool, repair-with-fill, asymmetric mutation, greedy seeding
- Date: 2026-11-12 | Milestone: M4 | Status: Accepted
- Context: The plan fixed the GA's outline: binary chromosome (D-010), tournament k = 3, uniform crossover 0.9, elitism 2%, 300 generations / 50 patience, population 100, under 60 s. The details still had to be decided. First trials with symmetric mutation (5 on / 5 off) and repair without fill never improved on the Greedy seed: almost every child was worse, because random drops lost good customers and nothing replaced them.
- Decision:
  - **Gene pool:** eligible customers with positive EP, plus all members of segments that have a minimum share (6,700 + negative-EP Growing/Dormant members in the default scenario). A negative-EP customer can only raise profit by meeting a minimum.
  - **Repair with fill:** hard limits → max shares → min shares → fill spare capacity with positive-EP customers in EP/C order → re-check shares, iterating until every row is feasible. When dropping because of a head-count limit, the engine drops by lowest EP. When dropping for the budget, it drops by lowest EP/C.
  - **Asymmetric bit-flip mutation:** about 30 genes switched on and 0.5 off per child. Repair then drops the weakest, so a mutation works as a set of swaps that test new customers instead of a random walk away from feasibility.
  - **Seeding:** 4 of the 100 chromosomes are the Greedy list and perturbed copies. The rest are random at the density the budget allows. The unseeded run is reported too.
  - **Fitness:** total EP minus a large penalty per unit of violation, a fallback that repair should make unused.
  - An optional `time_limit_s` is available for dashboard re-runs.
- Why: With these choices both seeded and unseeded runs reach the exact optimum in the default scenario (5 of 5 seeds), in about 11-16 s (90-107 generations). Across 40 random scenarios the GA averaged 99.6% of the optimum (minimum 96%) against Greedy's 98.3% (minimum 92%). Mutation settings tested: 10/1 and 20/2 also reached the optimum but took 1.5-2.5× longer; 5/5 never improved on its seed.
- Alternatives considered (and why not taken):
  - Symmetric bit-flip (5/5): children were almost always worse than their parents, so the search stalled.
  - Repair without fill: lists stayed under-filled after drops, which biased the search towards small lists.
  - Genes = all 9,041 eligible customers: larger chromosome, and a negative-EP customer only helps by meeting a minimum.
  - Penalty-only (no repair): most of the population would be infeasible and the search would be slower.
  - Unseeded only: works, but slower to converge, and seeding guarantees the GA is never worse than Greedy.
- Other possible alternatives (not evaluated / future options):
  - Swap-based local search (memetic GA) or adaptive mutation rates, if a scenario shows a persistent gap to the optimum.
- Consequences: The GA cannot do worse than Greedy (elitism plus the Greedy seed). Stressed scenarios with several binding share limits run longer (up to about 160 s in the notebook's "balanced mix" what-if), so the dashboard should set `time_limit_s`.
- Related: D-010, D-011, D-035, `config.GAConfig`, `optimize.run_ga`

## D-037: Exact MILP optimum as the benchmark; honest framing of the GA's gain
- Date: 2026-11-12 | Milestone: M4 | Status: Accepted
- Context: Q5 asks how much extra profit the optimised list earns. The acceptance criteria need "GA ≥ 98% of the MILP optimum", and the plan warned that greedy is near-optimal under a budget-only constraint.
- Decision: Solve the exact optimum with `scipy.optimize.milp` (HiGHS) over **all** eligible customers and the same constraints (time limit 180 s, relative gap 1e-6). Report every strategy's % of the optimum. The headline Q5 figure is GA vs Random (the proxy for an untargeted campaign), with Propensity, Rule-based and Greedy also shown. The notebook states plainly that in the default scenario most of the gain comes from ranking by EP per £ (Greedy reaches 99.96% of the optimum, and only the 6,000-contact cap binds at the optimum), and shows stressed what-if scenarios where the GA's gain over Greedy is material (+£1.6K to +£3.5K, Greedy 94-98% vs GA 98.4-99.9% of the optimum).
- Why: An exact optimum turns "the GA is good" into a measured claim. Solving over all eligible customers (not only the GA's gene pool) confirms that the gene-pool restriction loses nothing. The default problem solves to proven optimality in about 30 s.
- Alternatives considered (and why not taken):
  - LP relaxation bound only: an upper bound, not a list. It can't be audited by `check_constraints()`.
  - No exact benchmark: the GA's quality could not be verified.
  - Changing the default constraints so the GA wins by more: that would tune the scenario to the method instead of the business, so stressed cases are shown as what-ifs instead.
- Other possible alternatives (not evaluated / future options):
  - Make the MILP the production optimiser if runtime allows, keeping the GA for non-linear objectives (e.g. diminishing returns, channel-response interactions) that a MILP can't express directly.
- Consequences: The default results are: Random £60.7K (mean of 50 seeds, std £1.0K), Rule-based £83.8K, Propensity £91.2K, Greedy £103.75K, GA = MILP £103.79K. So the GA gives +£43.1K (+71%) over Random and +£12.5K (+14%) over Propensity. The pipeline takes about 55 s with the MILP, and the dashboard can skip the MILP when it re-runs.
- Related: D-012, D-017 (dashed MILP line on Screen 3), `optimize.milp_optimum`, `optimize.compare_strategies`, `notebooks/04_genetic_algorithm.ipynb`

## D-038: Dashboard architecture: scenario object, cached recompute, on-demand optimisers
- Date: 2026-11-12 | Milestone: M5 | Status: Accepted
- Context: The dashboard must take every figure from pipeline outputs, update when sliders change, and keep GA re-runs within the stated time. The campaign table and the four baselines recompute in about 2 s. The GA takes 12-60 s and the MILP 30-100 s, too slow to re-run on every slider move.
- Decision:
  - **One `Scenario` object** (`pacopt/scenario.py`) holds the economics, eligibility rules, campaign constraints and model choice. Its JSON form is the cache key. `build_table()` applies the eligibility rules, the model choice (both models' scores are already saved, so nothing is retrained) and the economics.
  - **Cached recompute:** `st.cache_data` caches the campaign table and the baselines (Random, Propensity, Greedy, Rule-based) for each scenario, so these update on every change.
  - **On-demand optimisers:** the GA and MILP run on a button press. Session results are kept per scenario, and the GA is capped at 30 s (`GAConfig.time_limit_s`).
  - **Saved results reused only on an exact match:** `pipeline.save_optimisation()` writes a fingerprint of the problem (eligible customers' EP, cost, channel, segment and protected flag, plus the constraints). `load_optimisation()` returns the saved GA/MILP results only when the fingerprint matches. So the default scenario opens with the full results instantly, and any change shows the baselines plus a "Run GA" prompt, never stale numbers.
  - **Navigation and sidebar:** `st.navigation` with page files in `app/views/` (not `pages/`, which Streamlit would also auto-list). Each page renders the shared sidebar. The scenario values live in persistent session keys (`p_*`), copied into the page's widgets and written back on change, because Streamlit drops a widget's state when you leave its page.
  - `compare_strategies(run_genetic=False, run_milp=False)` plus `with_optimisers()` split the comparison into its fast and slow parts.
- Why: Changes to the sidebar are reflected straight away, slow work runs only when asked, and a cached result can never be shown for a different scenario. The 30 s cap is half the plan's 60 s limit. In tests, a £30K-budget scenario reached 99.94% of the optimum within 20 s, and running to 60 s added only £1.
- Alternatives considered (and why not taken):
  - Re-run the GA on every change: 12-60 s of lag on each slider move.
  - Always show the saved default GA/MILP results: they would be wrong for any changed scenario.
  - A single page with tabs: one long script that recomputes everything at once, and a less clear structure for Screens 1-4.
  - Sidebar widgets in the entrypoint above `st.navigation`: Streamlit's AppTest drops those widgets on rerun, so the app couldn't be tested headlessly. Rendering the sidebar in each page works in both.
- Other possible alternatives (not evaluated / future options):
  - A background worker (thread or queue) so the GA doesn't block the page.
  - Persisting user-run scenarios to disk so that they can be shared.
- Consequences: The GA's result for an edited scenario depends on the time cap, and the time taken is shown. Screen 4 makes local what-if changes (budget, channel costs, spread, incentive) on top of the sidebar scenario. Ten AppTest tests cover every page, cross-page persistence, reset and fingerprint reuse.
- Related: D-016, D-034, D-036, D-037, `app/`, `pacopt/scenario.py`, `pipeline.save_optimisation`/`load_optimisation`, `tests/test_app.py`

## D-040: Validation design: reproducibility check, ablation, backtest, robustness, fairness review
- Date: 2026-11-12 | Milestone: M6 | Status: Accepted
- Context: Milestone 6 must show that the results can be trusted and reproduced. The checks: a clean-clone end-to-end run, leakage checks, constraint property tests, a backtest on actual outcomes, GA and economic robustness, and a fairness review. Disk space on the development machine was too limited for a second ~700 MB virtual environment.
- Decision:
  - **Reproducibility (`scripts/check_reproducibility.py`):** copy exactly the files git would commit (no processed data, artifacts or `.venv`) into a temp folder. Run `pacopt.pipeline` there from the raw CSV with the project interpreter, importing the clone's own `src`. Compare the metrics, campaign table, segments, every strategy's result and the problem fingerprint. `uv lock --check` separately confirms the lockfile.
  - **Leakage ablation (`evaluation.leakage_ablation`):** the same tuned LR on the chosen allow-list, then with `campaign`/`day`/`month` added, then with `duration` too. The leaky fits use the `allow_leaky=True` path, which exists only for this. `transforms_inside_pipeline()` checks that each calibrated fold holds a Pipeline whose first step is the ColumnTransformer.
  - **Property tests:** 25 random scenarios (customers, costs, eligibility, budget, capacities, segment maxima and minima, protected cap) run all five heuristic strategies through the independent checker, and 10 more stress the repair operator from empty to full chromosomes.
  - **Backtest (`evaluation.backtest`):** realised contribution = V_i summed over actual converters, minus C_i for every contact. Random is averaged over the same 50 seeds. Bootstrap 95% intervals use 2,000 resamples of each list.
  - **Robustness:** the GA is run with 5 seeds × seeded/unseeded against the MILP optimum. Ranking sensitivity re-derives the economics *and* the segments under ±25% and ±50% changes to spread, incentive and contact cost (Random uses 20 seeds and the GA is capped at 30 s per case).
  - **Fairness review:** targeting-rate ratios by age band and job, flagged below 0.5× or above 2× (groups under 30 customers are never flagged). `fairness_drivers()` shows the propensity, value and EP behind each skew.
- Why: Each check targets a specific way the prototype could mislead. Leakage would inflate accuracy; an infeasible list would break the comparison; miscalibration would make EP wrong; a lucky seed or one particular economic setting could flatter the GA; and targeting could be unfair. The clone check proves the README commands reproduce the numbers without relying on local state.
- Alternatives considered (and why not taken):
  - A second `uv sync` in the clone: the most literal "clean clone", but it needs ~700 MB, and the disk was full. Reusing the locked environment tests the code and data path, and `uv lock --check` covers the dependency spec. On a CI runner, `uv sync` in a fresh checkout is the fuller version.
  - A causal backtest (uplift): impossible without a control group (D-015). The backtest is framed as a calibration check on the chosen lists.
  - Hypothesis-based property testing: an extra dependency for the same coverage that seeded random scenarios give.
  - Enforcing fairness as constraints: not requested, and the observed skews are explained by propensity. The capability exists through segment-share constraints if a business owner wants it.
- Other possible alternatives (not evaluated / future options):
  - A GitHub Actions workflow running `uv sync` + `uv run pytest` + the reproducibility script on every push.
  - Time-based validation (train on earlier campaigns, test on later ones) if campaign dates were usable without leakage.
- Consequences: The full suite takes about 5-6 minutes (the ablation and GA-seed tests dominate). Notebook 05 holds the full 5-seed and sensitivity studies, which take about 10-15 minutes. Results: the clone reproduces exactly; ROC-AUC is 0.753 vs 0.776 (with campaign columns) vs 0.908 (with duration); the GA list had 891 expected vs 889 actual conversions; the GA reaches the optimum on 10 of 10 runs; the GA is first or tied in 13 of 13 sensitivity cases, while Propensity overtakes Greedy when contact costs halve; no fairness flags. Limitation found: with 66% of the eligible base selected, no group can exceed about 1.51x, so the 2x flag cannot fire in the default scenario. The share columns are reported alongside, and a share-based flag is a future option.
- Related: D-004, D-007, D-014, D-015, D-035, D-037, `evaluation.py`, `scripts/check_reproducibility.py`, `tests/test_validation.py`, `notebooks/05_validation.ipynb`, `README.md`
